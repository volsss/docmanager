# Глава 6. Побочные эффекты и асинхронность в Jetpack Compose

## 6.1. Что такое побочные эффекты

В предыдущих главах мы рассмотрели декларативную модель **Compose**.

Composable-функция описывает интерфейс на основе входных данных и состояния.

Однако реальные приложения должны выполнять действия, которые не ограничиваются построением интерфейса.

Например:

- отправлять сетевые запросы;
- записывать данные в аналитическую систему;
- подписываться на внешние источники данных;
- показывать `Snackbar`;
- запускать анимации;
- регистрировать слушатели событий;
- работать с системными API.

Такие операции могут изменять состояние внешних систем или взаимодействовать с ними. Их называют побочными эффектами (**Side Effects**).

Проблема заключается в том, что composable-функции могут выполняться повторно в результате рекомпозиции.

Поэтому произвольные побочные эффекты нельзя бездумно размещать непосредственно в теле composable-функции.

Рассмотрим пример неправильного подхода:

```kotlin
@Composable
fun UserScreen(userId: String) {
    val user = repository.loadUser(userId)

    Text(user.name)
}
```

Здесь загрузка данных непосредственно связана с выполнением composable-функции.

Если функция будет рекомпозирована, операция может выполниться повторно.

Правильнее разделить ответственность:

- ViewModel выполняет бизнес-операции;
- репозиторий отвечает за получение данных;
- Compose отображает состояние;
- специальные механизмы Compose используются для эффектов, непосредственно связанных с композицией.

## 6.2. Основные эффекты Compose

Compose предоставляет несколько API для управления побочными эффектами.

| API | Назначение |
|---|---|
| `LaunchedEffect` | Запуск coroutine при входе в композицию и при изменении ключей |
| `rememberCoroutineScope` | Получение coroutine scope, привязанного к композиции |
| `DisposableEffect` | Регистрация и освобождение ресурсов |
| `SideEffect` | Выполнение операции после успешной композиции |
| `rememberUpdatedState` | Получение актуального значения внутри долгоживущего эффекта |
| `produceState` | Преобразование внешних источников данных в Compose State |
| `snapshotFlow` | Преобразование Compose State в Kotlin Flow |

Каждый механизм предназначен для определённого сценария. Их не следует использовать как взаимозаменяемые инструменты.

## 6.3. LaunchedEffect

`LaunchedEffect` позволяет запускать coroutine, жизненный цикл которой связан с присутствием соответствующего composable-вызова в композиции.

Пример:

```kotlin
@Composable
fun TimerScreen() {
    var seconds by remember {
        mutableIntStateOf(0)
    }

    LaunchedEffect(Unit) {
        while (true) {
            delay(1000)
            seconds++
        }
    }

    Text("Прошло секунд: $seconds")
}
```

Разберём последовательность:

1. `TimerScreen` попадает в композицию.
2. Запускается coroutine внутри `LaunchedEffect`.
3. Каждую секунду значение `seconds` увеличивается.
4. Compose обновляет интерфейс.
5. Когда соответствующий участок покидает композицию, coroutine отменяется.

`LaunchedEffect` удобен для операций, которые должны выполняться, пока composable-компонент находится в композиции.

Например:

- ожидание завершения анимации;
- наблюдение за состоянием прокрутки;
- запуск UI-операции после появления компонента;
- выполнение suspend-операции, жизненный цикл которой связан с компонентом.

### 6.3.1. Ключи LaunchedEffect

У `LaunchedEffect` есть механизм ключей.

Если ключ изменяется, текущая coroutine отменяется и запускается заново.

```kotlin
@Composable
fun UserScreen(userId: String) {
    LaunchedEffect(userId) {
        println("Изменился пользователь: $userId")
    }
}
```

При изменении `userId` эффект будет перезапущен.

Это важно, когда операция зависит от конкретного значения.

Можно использовать несколько ключей:

```kotlin
LaunchedEffect(userId, categoryId) {
    // Операция зависит от двух значений.
}
```

Эффект перезапустится при изменении любого ключа.

### 6.3.2. Unit как ключ

Часто можно встретить:

```kotlin
LaunchedEffect(Unit) {
    // Выполняется один раз для данного экземпляра эффекта.
}
```

Это означает, что эффект не будет перезапущен из-за обычной рекомпозиции, поскольку ключ `Unit` остаётся неизменным.

Но важно помнить: при выходе из композиции и последующем повторном входе создаётся новый экземпляр эффекта.

Поэтому `LaunchedEffect(Unit)` не означает "один раз за всё время существования приложения".

### 6.3.3. Почему ключи важны

Рассмотрим:

```kotlin
LaunchedEffect(userId) {
    repository.loadUser(userId)
}
```

Если забыть передать `userId` в качестве ключа:

```kotlin
LaunchedEffect(Unit) {
    repository.loadUser(userId)
}
```

то при изменении `userId` уже запущенный эффект не перезапустится.

Он продолжит работать с тем значением, которое было доступно при его запуске.

Поэтому все изменяемые значения, от которых должна зависеть операция, необходимо учитывать среди ключей.

Если изменение значения не должно перезапускать операцию, но внутри неё требуется использовать актуальное значение, применяется `rememberUpdatedState`.

## 6.4. rememberCoroutineScope

Иногда coroutine необходимо запускать не автоматически при входе компонента в композицию, а в ответ на действие пользователя.

Например, при нажатии кнопки необходимо показать `Snackbar`.

Для таких случаев используется `rememberCoroutineScope`.

```kotlin
@Composable
fun MessageScreen() {
    val snackbarHostState = remember {
        SnackbarHostState()
    }

    val scope = rememberCoroutineScope()

    Scaffold(
        snackbarHost = {
            SnackbarHost(snackbarHostState)
        }
    ) { padding ->
        Button(
            modifier = Modifier.padding(padding),
            onClick = {
                scope.launch {
                    snackbarHostState.showSnackbar(
                        message = "Данные сохранены"
                    )
                }
            }
        ) {
            Text("Показать сообщение")
        }
    }
}
```

`rememberCoroutineScope()` возвращает scope, который:

- связан с текущим местом вызова в композиции;
- сохраняется между рекомпозициями;
- отменяется, когда соответствующий участок покидает композицию.

### Чем rememberCoroutineScope отличается от LaunchedEffect

`LaunchedEffect` подходит для запуска эффекта как реакции на появление компонента или изменение ключей.

`rememberCoroutineScope` подходит для запуска coroutine из обработчика события, например `onClick`.

Пример:

| Сценарий | Инструмент |
|---|---|
| Запустить анимацию при появлении компонента | `LaunchedEffect` |
| Наблюдать изменение позиции прокрутки | `LaunchedEffect` + `snapshotFlow` |
| Показать Snackbar после нажатия | `rememberCoroutineScope` |
| Отменить coroutine при уходе компонента | Оба инструмента автоматически учитывают композицию |

### Важное архитектурное замечание

Не следует переносить бизнес-запросы во `ViewModel` в `rememberCoroutineScope` только ради того, чтобы запустить coroutine из UI.

Если операция относится к бизнес-логике, обработчик должен вызвать метод `ViewModel`, а уже `ViewModel` должна запускать работу в `viewModelScope`.

`rememberCoroutineScope` прежде всего предназначен для операций UI-уровня.

## 6.5. rememberUpdatedState

`rememberUpdatedState` применяется, когда эффект должен продолжать работать, но использовать актуальное значение параметра после рекомпозиции.

Рассмотрим пример.

Есть экран, который автоматически закрывается через пять секунд.

```kotlin
@Composable
fun WelcomeScreen(
    onTimeout: () -> Unit
) {
    LaunchedEffect(Unit) {
        delay(5000)
        onTimeout()
    }
}
```

Проблема: если callback `onTimeout` изменится во время работы эффекта, coroutine продолжит использовать захваченную ранее ссылку.

Чтобы использовать актуальный callback, применим `rememberUpdatedState`.

```kotlin
@Composable
fun WelcomeScreen(
    onTimeout: () -> Unit
) {
    val currentOnTimeout by rememberUpdatedState(onTimeout)

    LaunchedEffect(Unit) {
        delay(5000)
        currentOnTimeout()
    }
}
```

Теперь изменение `onTimeout` не перезапускает эффект, но при завершении задержки вызывается актуальная версия функции.

Основная идея:

- ключ эффекта определяет, когда требуется перезапуск;
- `rememberUpdatedState` позволяет читать актуальное значение без перезапуска.

Это особенно полезно для долгоживущих операций.

## 6.6. DisposableEffect

`DisposableEffect` применяется тогда, когда необходимо зарегистрировать внешний ресурс и гарантированно освободить его при завершении эффекта.

Например:

- зарегистрировать слушатель;
- подписаться на внешний источник;
- добавить lifecycle observer;
- подключить callback;
- освободить ресурс при удалении компонента.

Пример:

```kotlin
@Composable
fun LifecycleObserver(
    lifecycleOwner: LifecycleOwner,
    onStart: () -> Unit
) {
    val currentOnStart by rememberUpdatedState(onStart)

    DisposableEffect(lifecycleOwner) {
        val observer = LifecycleEventObserver { _, event ->
            if (event == Lifecycle.Event.ON_START) {
                currentOnStart()
            }
        }

        lifecycleOwner.lifecycle.addObserver(observer)

        onDispose {
            lifecycleOwner.lifecycle.removeObserver(observer)
        }
    }
}
```

Разберём работу:

1. Composable входит в композицию.
2. Создаётся observer.
3. Observer регистрируется у `lifecycleOwner`.
4. При завершении эффекта вызывается `onDispose`.
5. Observer удаляется.

Если `lifecycleOwner` меняется, эффект сначала освобождает прежний ресурс, а затем создаёт новый.

В этом примере используется Android Lifecycle API, поэтому компонент является платформенно-зависимым.

Для общего **Compose Multiplatform**-кода можно использовать `DisposableEffect` с собственными multiplatform-совместимыми интерфейсами подписок.

### Почему недостаточно LaunchedEffect

`LaunchedEffect` управляет coroutine.

`DisposableEffect` управляет жизненным циклом регистрации и освобождения внешних ресурсов.

Если необходимо зарегистрировать слушатель и удалить его при завершении работы, `DisposableEffect` обычно подходит лучше.

## 6.7. SideEffect

`SideEffect` позволяет выполнить действие после успешной композиции.

Пример:

```kotlin
@Composable
fun UserScreen(
    user: UserUiModel,
    analytics: Analytics
) {
    SideEffect {
        analytics.setCurrentUser(user.id)
    }

    Text(user.name)
}
```

Здесь после успешной композиции вызывается операция обновления внешнего объекта аналитики.

> [!IMPORTANT] `SideEffect` выполняется после каждой успешной рекомпозиции соответствующего компонента.
> 
> Поэтому его нельзя использовать для отправки одноразовых событий при каждом появлении нового состояния.

Например, следующий подход может привести к многократной отправке одного и того же события:

```kotlin
SideEffect {
    analytics.logEvent("purchase_completed")
}
```

Для регистрации изменений внешнего состояния `SideEffect` подходит, а для одноразовых действий необходимо выбирать другой механизм.

## 6.8. produceState

`produceState` позволяет преобразовывать внешние источники данных в состояние Compose.

Он полезен, когда некоторый источник не является **Compose State**, но его значение требуется отображать в интерфейсе.

Например:

```kotlin
@Composable
fun rememberUserName(
    userRepository: UserRepository,
    userId: String
): State<String?> {
    return produceState<String?>(
        initialValue = null,
        userRepository,
        userId
    ) {
        value = userRepository.getUserName(userId)
    }
}
```

Использование:

```kotlin
@Composable
fun UserNameScreen(
    repository: UserRepository,
    userId: String
) {
    val userName by rememberUserName(
        repository,
        userId
    )

    if (userName == null) {
        CircularProgressIndicator()
    } else {
        Text(userName.orEmpty())
    }
}
```

`produceState`:

- создаёт **Compose State**;
- запускает producer при входе в композицию;
- отменяет работу при выходе;
- перезапускает producer при изменении ключей.

Если необходимо наблюдать callback-based источник данных, можно использовать `awaitDispose` для отмены подписки.

### Когда не нужно использовать produceState

Если источник уже является `StateFlow`, обычно достаточно `collectAsState()` или `collectAsStateWithLifecycle()`.

Не стоит оборачивать каждый `Flow` в `produceState` без необходимости.

## 6.9. snapshotFlow

`Snapshot State` принадлежит **Compose Runtime**, а `Flow` — **Kotlin** Coroutines.

`snapshotFlow` позволяет преобразовывать значения **Compose State** в холодный **Kotlin Flow**.

Например, необходимо отслеживать прокрутку списка.

```kotlin
@Composable
fun MessageList(
    messages: List<MessageUiModel>
) {
    val listState = rememberLazyListState()

    LaunchedEffect(listState) {
        snapshotFlow {
            listState.firstVisibleItemIndex
        }
            .distinctUntilChanged()
            .collect { index ->
                println("Первый видимый элемент: $index")
            }
    }

    LazyColumn(state = listState) {
        items(
            items = messages,
            key = { it.id }
        ) { message ->
            MessageRow(message)
        }
    }
}
```

Здесь:

1. `snapshotFlow` наблюдает за **Snapshot State**.
2. При изменении наблюдаемого значения `Flow` выдаёт новое значение.
3. `distinctUntilChanged()` исключает повторные соседние значения.
4. `collect` обрабатывает полученные данные.

### Пример: аналитика прокрутки

```kotlin
LaunchedEffect(listState) {
    snapshotFlow {
        listState.firstVisibleItemIndex > 0
    }
        .distinctUntilChanged()
        .filter { it }
        .collect {
            analytics.logEvent("scrolled_past_first_item")
        }
}
```

Теперь событие отправляется при переходе списка за первый элемент, а не при каждом обновлении индекса.

`snapshotFlow` не следует использовать как универсальную замену `StateFlow`. Он предназначен именно для чтения **Compose Snapshot State**.

## 6.10. Эффекты и MVVM

Теперь необходимо определить, где именно должны выполняться операции.

Предположим, пользователь нажимает кнопку обновления списка.

Неправильный вариант:

```kotlin
@Composable
fun NewsScreen() {
    val scope = rememberCoroutineScope()

    Button(
        onClick = {
            scope.launch {
                repository.refreshNews()
            }
        }
    ) {
        Text("Обновить")
    }
}
```

Здесь UI напрямую обращается к репозиторию и выполняет бизнес-операцию.

Более правильный вариант:

```kotlin
@Composable
fun NewsScreen(
    onRefresh: () -> Unit
) {
    Button(
        onClick = onRefresh
    ) {
        Text("Обновить")
    }
}
```

`ViewModel`:

```kotlin
class NewsViewModel(
    private val repository: NewsRepository
) : ViewModel() {

    fun refreshNews() {
        viewModelScope.launch {
            repository.refreshNews()
        }
    }
}
```

`Route`:

```kotlin
@Composable
fun NewsRoute(
    viewModel: NewsViewModel = viewModel()
) {
    NewsScreen(
        onRefresh = viewModel::refreshNews
    )
}
```

В результате:

- UI только передаёт действие;
- `ViewModel` управляет бизнес-операцией;
- репозиторий получает данные;
- новое состояние публикуется через `StateFlow`;
- Compose отображает обновлённый результат.

### Что делать с одноразовыми UI-сообщениями

Например, необходимо показать `Snackbar` после неудачного сохранения.

Современная архитектурная рекомендация **Android** — не строить UI на ненадёжном потоке одноразовых событий из `ViewModel`. Вместо этого следует представлять результат обработки события в UI State.

Пример:

```kotlin
data class ProfileUiState(
    val isSaving: Boolean = false,
    val message: String? = null
)
```

После обработки действия `ViewModel` публикует состояние с сообщением.

UI отображает `Snackbar` и сообщает о том, что сообщение было обработано:

```kotlin
LaunchedEffect(state.message) {
    val message = state.message ?: return@LaunchedEffect

    snackbarHostState.showSnackbar(message)

    onMessageShown()
}
```

Такой подход делает взаимодействие более предсказуемым и позволяет явно управлять жизненным циклом сообщения.

## 6.11. Краткая таблица выбора эффектов

| Ситуация | Инструмент |
|---|---|
| Запустить coroutine при появлении компонента | `LaunchedEffect` |
| Перезапустить операцию при изменении параметра | `LaunchedEffect` с ключом |
| Запустить coroutine после нажатия | `rememberCoroutineScope` |
| Использовать актуальный callback без перезапуска эффекта | `rememberUpdatedState` |
| Зарегистрировать и освободить слушатель | `DisposableEffect` |
| Обновить внешний объект после композиции | `SideEffect` |
| Преобразовать callback-based источник в Compose State | `produceState` |
| Преобразовать **Compose** `State` в `Flow` | `snapshotFlow` |

## 6.12. Подготовка к Compose Multiplatform

Большинство рассмотренных эффектов относятся к **Compose Runtime** и доступны в общем Compose-коде.

Например:

- `LaunchedEffect`;
- `rememberCoroutineScope`;
- `rememberUpdatedState`;
- `DisposableEffect`;
- `SideEffect`;
- `produceState`;
- `snapshotFlow`.

При этом конкретный источник эффекта может быть платформенным.

Например, регистрацию **Android BroadcastReceiver** необходимо выполнять в Android-части приложения.

В общем коде желательно использовать абстракции, а платформенную реализацию передавать через зависимости или платформенные реализации интерфейсов.

Также необходимо различать:

- жизненный цикл композиции;
- жизненный цикл `ViewModel`;
- жизненный цикл платформенного приложения.

Эти жизненные циклы могут не совпадать.

## 6.13. Типичные ошибки

1. Выполнять сетевые запросы непосредственно в теле composable-функции.
2. Использовать `LaunchedEffect(Unit)` для любой операции без анализа ключей.
3. Запускать бизнес-операции из `rememberCoroutineScope`, обходя ViewModel.
4. Не освобождать ресурсы в `DisposableEffect`.
5. Использовать `SideEffect` для отправки одноразовых событий.
6. Пропускать изменяемые зависимости в списке ключей эффекта.
7. Не использовать `rememberUpdatedState` для актуального callback в долгоживущем эффекте.
8. Оборачивать существующий StateFlow в `produceState` без необходимости.
9. Использовать `snapshotFlow` для наблюдения обычных Kotlin-переменных, не являющихся Compose State.
10. Игнорировать отмену coroutine при изменении ключей или выходе компонента из композиции.
