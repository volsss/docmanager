# Практическое задание по лабораторной работе № 4

## Разработка мобильного приложения с использованием Jetpack Compose

Практическое задание разработано на основе глав лабораторной работы № 4, посвящённых декларативному интерфейсу **Jetpack Compose**, composable-функциям, компоновке интерфейсов, UI-компонентам, управлению состоянием, побочным эффектам, спискам, навигации, архитектуре **MVVM** и адаптивному дизайну.

Задание состоит из обязательной части, выполняемой всеми студентами, и 30 индивидуальных вариантов. Все варианты имеют одинаковый объём и сложность: отличаются только предметной областью и типами отображаемых данных.

Цель работы — получить практические навыки разработки полноценного пользовательского интерфейса мобильного приложения с использованием **Jetpack Compose**, управления состоянием, организации архитектуры **MVVM** и реализации интерактивного взаимодействия с пользователем.

## Обязательные требования ко всем вариантам

### 1. Общая структура приложения

1. Разработать мобильное приложение на **Kotlin** с использованием **Jetpack Compose** и **Material Design 3**.
2. Приложение должно иметь название, соответствующее индивидуальному варианту.
3. Реализовать не менее трёх основных экранов:
   - главный экран со списком объектов предметной области;
   - экран подробной информации об объекте;
   - экран добавления или редактирования объекта.
4. Предусмотреть возможность перехода между экранами и возврата на предыдущий экран.
5. Интерфейс должен быть логически организован, содержать понятные заголовки и элементы управления.

### 2. Composable-функции и композиция

1. Каждый основной экран реализовать в виде отдельной composable-функции.
2. Повторяющиеся элементы интерфейса вынести в отдельные composable-компоненты.
3. Необходимо использовать параметры для передачи данных в компоненты.
4. Пользовательские действия передавать через функции обратного вызова.
5. Не допускать выполнения бизнес-логики и произвольных побочных действий непосредственно в теле composable-функций.
6. Обеспечить корректную работу композиции и рекомпозиции при изменении состояния.

### 3. Компоновка интерфейса и Modifier

1. Использовать основные контейнеры **Jetpack Compose**:
   - `Column`;
   - `Row`;
   - `Box`.
2. Применять `Modifier` для настройки размеров, отступов, выравнивания, фона, формы и интерактивности элементов.
3. Использовать подходящие варианты `Arrangement` и `Alignment`.
4. Обеспечить корректное размещение элементов при изменении размеров экрана.
5. Не допускать наложения элементов и выхода содержимого за границы доступной области.

### 4. Основные UI-компоненты

1. Использовать `Text` для отображения текстовой информации.
2. Использовать кнопки `Button`, `OutlinedButton` или `TextButton` для выполнения действий.
3. Использовать `TextField` или `OutlinedTextField` для ввода данных.
4. Использовать подходящие компоненты **Material Design 3**:
   - `Card`;
   - `IconButton`;
   - `Checkbox`;
   - `Switch`;
   - `RadioButton`;
   - `FloatingActionButton`.
5. Обеспечить корректное отображение доступных и недоступных элементов управления.
6. Предусмотреть отображение сообщений об ошибках и подтверждений действий.

### 5. Управление состоянием

1. Реализовать управление локальным состоянием с использованием `remember` и `mutableStateOf`.
2. Для состояния, которое должно сохраняться при пересоздании Activity или изменении конфигурации, использовать `rememberSaveable` либо соответствующий механизм хранения состояния.
3. Реализовать поднятие состояния (State Hoisting) для повторно используемых компонентов.
4. Состояние основных экранов должно храниться и предоставляться через `ViewModel`.
5. Обеспечить однонаправленный поток данных: состояние передаётся в интерфейс, а пользовательские действия передаются обратно в `ViewModel`.
6. При изменении данных интерфейс должен обновляться автоматически без ручного обновления экранов.

### 6. Побочные эффекты и асинхронность

1. Использовать `LaunchedEffect` для выполнения UI-операций, связанных с жизненным циклом композиции.
2. Использовать `rememberCoroutineScope` для запуска coroutine по пользовательскому действию, если это необходимо.
3. При необходимости использовать `DisposableEffect` для регистрации и удаления слушателей или подписок.
4. Не выполнять длительные операции непосредственно в composable-функциях.
5. Предусмотреть обработку состояний загрузки и ошибок.
6. При использовании coroutine обеспечить корректную отмену операций при завершении соответствующего жизненного цикла.

### 7. Списки и навигация

1. Отображать основной набор объектов с помощью `LazyColumn`.
2. Для горизонтальных категорий или фильтров использовать `LazyRow`.
3. При необходимости группировки объектов использовать `LazyVerticalGrid`.
4. Для элементов списка предусмотреть стабильные уникальные ключи `key`.
5. Реализовать переход с элемента списка на экран подробной информации.
6. Предусмотреть возврат к списку с сохранением его состояния и позиции прокрутки.
7. Реализовать поиск или фильтрацию элементов списка.

### 8. Архитектура MVVM

1. Организовать приложение с использованием архитектуры MVVM.
2. Разделить приложение на следующие логические слои:
   - UI Layer — пользовательский интерфейс;
   - Domain Layer — модели предметной области и бизнес-правила;
   - Data Layer — получение и хранение данных.
3. Создать `ViewModel` для управления состоянием основных экранов.
4. Создать репозиторий для предоставления данных интерфейсу.
5. Не размещать бизнес-логику непосредственно в composable-функциях.
6. Обеспечить независимость UI-компонентов от конкретного способа хранения данных.

### 9. Темы и адаптивный интерфейс

1. Использовать `MaterialTheme`.
2. Создать собственную цветовую схему приложения.
3. Настроить типографику и формы компонентов.
4. Использовать роли цветов из `ColorScheme`, а не задавать произвольные цвета для каждого элемента.
5. Предусмотреть светлую и тёмную темы.
6. Обеспечить читаемость интерфейса и удобство взаимодействия на экранах различного размера.

### 10. Демонстрационные данные

1. Приложение должно содержать не менее 10 демонстрационных объектов предметной области.
2. Демонстрационные данные должны быть представлены в виде моделей Kotlin.
3. Каждый объект должен иметь уникальный идентификатор.
4. Все демонстрационные объекты должны отображаться в основном списке.
5. После добавления, редактирования или удаления объекта соответствующие изменения должны отражаться в интерфейсе.

## Требования — итоговые требования для всех вариантов

Для успешного выполнения практического задания необходимо реализовать единый минимальный функциональный набор независимо от индивидуального варианта.

### 1. Функциональные требования

1. Приложение должно отображать список не менее 10 демонстрационных объектов.
2. Пользователь должен иметь возможность просматривать подробную информацию об объекте.
3. Пользователь должен иметь возможность добавлять новые объекты.
4. Пользователь должен иметь возможность редактировать существующие объекты.
5. Пользователь должен иметь возможность удалять объекты с подтверждением действия.
6. Должен быть реализован поиск по одному или нескольким текстовым полям объекта.
7. Должна быть реализована фильтрация объектов по одному или нескольким атрибутам.
8. После изменения данных интерфейс должен автоматически обновляться.
9. Должны быть предусмотрены состояния пустого списка, загрузки и ошибки.
10. При возврате на экран списка должны сохраняться актуальные данные и позиция прокрутки.

### 2. Требования к интерфейсу

1. Использовать Jetpack Compose и Material Design 3.
2. Реализовать минимум три основных экрана.
3. Использовать composable-функции для организации интерфейса.
4. Использовать `Column`, `Row`, `Box` и `Modifier` для компоновки.
5. Использовать `LazyColumn` для отображения основного списка.
6. Использовать `Card` или аналогичный компонент для представления объектов.
7. Реализовать навигацию между экранами.
8. Обеспечить корректную работу интерфейса при изменении размеров экрана.
9. Реализовать светлую и тёмную темы.
10. Обеспечить визуальную согласованность интерфейса.

### 3. Требования к архитектуре

1. Использовать архитектуру MVVM.
2. Создать модели предметной области.
3. Реализовать `ViewModel` для управления состоянием экранов.
4. Реализовать репозиторий для предоставления данных.
5. Разделить UI, бизнес-логику и работу с данными.
6. Использовать State Hoisting для повторно используемых компонентов.
7. Обеспечить однонаправленный поток данных.
8. Не размещать бизнес-логику непосредственно в composable-функциях.

### 4. Требования к управлению состоянием

1. Использовать `remember` и `mutableStateOf` для локального состояния.
2. Использовать `rememberSaveable` для состояния, которое должно сохраняться при пересоздании интерфейса.
3. Использовать состояние `ViewModel` для данных экранов.
4. Обеспечить корректную рекомпозицию при изменении состояния.
5. Не изменять данные напрямую без соответствующего механизма обновления состояния.

### 5. Требования к качеству реализации

1. Код должен быть структурирован и понятен.
2. Повторяющиеся элементы интерфейса должны быть вынесены в отдельные компоненты.
3. Необходимо использовать понятные имена переменных, функций и классов.
4. Необходимо предусмотреть проверку корректности вводимых данных.
5. Необходимо исключить возможность сохранения некорректных или пустых обязательных полей.
6. Необходимо обеспечить корректную обработку пользовательских действий.
7. Приложение должно запускаться без критических ошибок.
